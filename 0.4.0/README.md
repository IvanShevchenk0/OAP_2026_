# Лабораторна робота №4 — версія 0.4.0

Ця версія реалізована як SPA з фронтендом на TypeScript і бекендом на Express + SQL.js.

## Структура
- `index.html` — основна сторінка, що завантажує зібраний `dist/app.js`.
- `app.ts` — фронтенд-логіка, робота з формами, таблицями, фільтрацією та деталями.
- `apiClient.ts` — типізований HTTP-клієнт з підтримкою таймауту та стандартних ProblemDetails-помилок.
- `shared/dtos.ts` — загальні типи DTO між фронтендом і бекендом.
- `backend/src` — серверна частина Express, маршрути, сервіси, репозиторії, обробка помилок.

## Запуск фронтенду
1. Перейдіть у папку `0.4.0`.
2. Встановіть залежності:

```bash
npm install
```

3. Зберіть фронтенд:

```bash
npm run build
```

4. Відкрийте `index.html` у браузері або сервируйте папку `0.4.0` через локальний веб-сервер.

> Скрипт збирання компілює `app.ts` та `apiClient.ts` у `dist/app.js` і `dist/apiClient.js`.

## Запуск бекенду
1. Перейдіть у папку `0.4.0/backend`.
2. Встановіть залежності:

```bash
npm install
```

3. Запустіть сервер у режимі розробки:

```bash
npm run dev
```

4. Або зберіть і запустіть продакшн:

```bash
npm run build
npm run start
```

Сервер доступний за адресою `http://localhost:3000`.

## API

### Версія 1 (v1)
- `GET /api/v1/software` – отримати список ПЗ
- `GET /api/v1/software/:id` – отримати деталі ПЗ за ID
- `POST /api/v1/software` – створити нове ПЗ
- `PUT /api/v1/software/:id` – оновити ПЗ
- `DELETE /api/v1/software/:id` – видалити ПЗ

### Версія 0 (без версії)
- `GET /api/software` – отримати список ПЗ (alias до /api/v1/software)
- `GET /api/users` – отримати список користувачів
- `GET /api/categories` – отримати список категорій

## Приклади запитів

### Отримати список ПЗ
```bash
curl http://localhost:3000/api/v1/software
```

### Отримати одне ПЗ за ID
```bash
curl http://localhost:3000/api/v1/software/1
```

### Створити нове ПЗ
```bash
curl -X POST http://localhost:3000/api/v1/software \
  -H "Content-Type: application/json" \
  -d '{"name":"VS Code","version":"1.90","license":"MIT","seats":10,"comment":"Editor","categoryId":"1"}'
```

### Оновити ПЗ
```bash
curl -X PUT http://localhost:3000/api/v1/software/1 \
  -H "Content-Type: application/json" \
  -d '{"version":"1.91","seats":15}'
```

### Видалити ПЗ
```bash
curl -X DELETE http://localhost:3000/api/v1/software/1
```

### Обробка помилок
При помилці бекенд повертає відповідь у форматі ProblemDetails:
```json
{
  "status": 400,
  "title": "VALIDATION_ERROR",
  "detail": "Помилка валідації даних",
  "errors": [
    { "field": "name", "message": "Назва обов'язкова" }
  ]
}
```

## Особливості реалізації
- **Версіонування API**: мінімум /api/v1/ для основних ендпоінтів, з alias-маршрутами для зворотної сумісності.
- **TypeScript**: типізований фронтенд та бекенд з спільною папкою `shared/dtos.ts`.
- **Централізована обробка помилок**: бекенд використовує middleware для уніфікації відповідей з ProblemDetails.
- **AbortController таймаут**: фронтенд має таймаут 12 секунд для запитів та корректно обробляє скасування.
- **CORS**: налаштований на конкретні origin, явні методи (GET, POST, PUT, DELETE) та заголовки без використання "*".
- **Валідація DTO**: як на сервері (сервер-сайд), так і на клієнті (клієнт-сайд) з показом помилок по полях.
- На фронтенді реалізовано: фільтр по ліцензії, пошук, редагування, видалення та деталі ПЗ.
- Клієнт `apiClient.ts` обробляє JSON відповідь, викидає `ApiClientError` при неуспішному HTTP-статусі.

## Правила сумісності DTO

Для забезпечення стабільного контракту між фронтендом та бекендом дотримуємось принципів:

1. **Не видаляй і не перейменовуй поля**: якщо поле вже використовується фронтендом (наприклад, `name`, `version`), воно мусить залишатися в бекенді з тим же типом.

2. **Додавай нові поля як опціональні**: нові поля можуть додаватися з дефолтними значеннями або як опціональні (Partial типи), щоб не ламати старих клієнтів.

3. **Зберігай структуру відповідей**: список завжди повертається як `{ data: T[], meta?: {...} }`, а один елемент як `{ data: T }`. Ніколи не міняй цю структуру.
